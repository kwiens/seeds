# Architecture

Seeds is a Next.js 16 App Router application for one city. It lets residents
propose place-based community projects, gather support for them, and run them
through a Seed → Sprout → Tree lifecycle with a private team workspace. This
document explains how the code is organized, where the rules live, and how to
add to it without duplicating them.

## One deployment per city

Seeds is **not** multi-tenant. Each city runs its own deployment with its own
database, Blob stores and domain. City-specific values live in [`config/`](../config/README.md);
everything else is shared product code. This keeps the data model simple (no
`city_id` on every table, no cross-tenant query bugs) and keeps each city in
control of its own data and admins. If a hosted multi-city service is ever
wanted, it would be built as a layer above this app, not inside it.

## Layers

```
config/           City identity, taxonomy, copy, deployment ids   ← edit per city
app/              Routes. Server components by default.
components/       UI. shadcn/ui primitives in components/ui/.
lib/
  routes.ts       Every URL the app links to or revalidates
  session.ts      Pure session helpers (isAdmin, isSignedIn)
  auth-utils.ts   Participant-table capability checks
  auth-guards.ts  requireAdmin() for admin-only actions
  project-access.ts  The project authorization model (see below)
  revalidate.ts   revalidateProject(): one call after any project mutation
  actions/        "use server" mutations. One file per domain.
  db/
    schema.ts     Drizzle schema
    queries/      Read-only functions; filters.ts has shared where-fragments
    migrations/   Generated by drizzle-kit, committed with the schema change
  validations/    Zod schemas for every form and action input
```

Dependencies point downward: `app` → `components` → `lib` → `config`.
`config` imports nothing from the app except icon components and the
`SeedIconName` type.

## Data model

One `projects` table carries a project through its whole life. Stage
(`seed | sprout | tree`), approval (`draft | pending | approved`) and
`archivedAt` are three independent axes, never combined into one status enum.
Capabilities unlock by stage; they never fork into parallel tables.

Satellite tables hang off `projects` with cascading deletes:

| Table | Holds |
| --- | --- |
| `project_participants` | One row per person per role: supporters, gardeners, team roles, and name-only people from the project form |
| `project_updates` | Public progress posts and private team posts (`visibility`), with replies via `parent_id` |
| `project_comments` | Public "insights" with one level of replies |
| `project_budgets` | Proposed and final line-item budgets (Sprout+) |
| `project_events` | Team calendar (Sprout+) |
| `project_invites` | Shareable role invites, claimed atomically |
| `project_activity_reads` | Per-user read markers for the team feed |
| `project_approvals` | Who approved what, when |
| `project_update_file_deletions` | Outbox for private Blob cleanup |
| `site_settings` | Key/value: homepage phase, banner, Harvest Fest page |

`projects.category` is plain text validated against `config/categories.ts`,
so a city can define its own taxonomy without a migration. `badges` is a JSON
array of keys from `config/badges.ts`.

## Authorization

Three site roles (`user`, `council`, `admin`) and per-project participant
roles combine into two project capabilities. `lib/project-access.ts` is the
single place that computes them; pages, API routes and actions all call it.

| Capability | Who | Unlocks |
| --- | --- | --- |
| **manage** | Admins; active `gardener` or `co_gardener` | Edit the project, post public updates, see supporter emails, moderate insights, budgets, events, team roster |
| **team** | Everyone who can manage, plus any other active non-supporter role, Council, admins | Read and post in the private team workspace, upload and download attachments |

**team** is only ever true for an unarchived Sprout or Tree. The guard folds
that stage-and-archive rule in, so no caller re-implements it. Admin-only
operations (seating a Steward, deleting team posts, lifecycle changes) check
`isAdmin(session)` or go through `requireAdmin()`.

Read access is separate and lenient: anyone can read a pending or approved
project. Drafts and archived projects are visible only to managers
(`lib/project-read-access.ts`). The same rule as a SQL fragment is
`publicProject()` in `lib/db/queries/filters.ts`.

## Server actions

Every mutation is a `"use server"` function in `lib/actions/` and follows the
same shape:

```ts
export async function saveThing(projectId: string, data: unknown): Promise<ActionResult> {
  const access = await requireProjectAccess(projectId, {
    level: "manage",            // or "team" / "admin"
    requireWorkspace: true,     // Sprout+ only; default true for "team"
    forbidden: "…",             // optional per-action wording
  });
  if ("error" in access) return access;

  const parsed = thingSchema.safeParse(data);
  if (!parsed.success) return { error: firstIssue(parsed) };

  await db.insert(things).values({ … });

  revalidateProject(projectId);
  return { success: true };
}
```

- Results are `ActionResult<T>` from `lib/actions/result.ts`: `{ error }` or
  `{ success: true, ...payload }`. Components check `result.error`.
- Admin-only actions call `requireAdmin()` and **throw** on failure. An
  unauthorized admin call is a bug or an attack, not a form error.
- When the project comes from a related row (an event, an update), pass it
  to `checkProjectAccess(session, row.project, …)` instead of looking it up
  again. Select `id`, `stage` and `archivedAt` on the relation.
- After a mutation call `revalidateProject(id)`. It invalidates the public
  page tree, the explorer and stage listings, the admin table, the dashboard
  and the workspace tree. Do not hand-write `revalidatePath` strings.
- Build URLs with `routes` from `lib/routes.ts`. Nothing else should contain
  `/seeds/` or `/dashboard/projects/`.

## Reads

Queries are plain async functions in `lib/db/queries/`, one file per domain.
Collection views paginate at the database, filter at the database and select
only the columns they render (see the Production Scale Contract in
`AGENTS.md`). Recurring access conditions live in `filters.ts`
(`publicProject`, `indexableProject`, `notArchived`, `activeSupporter`,
`activeTeamMember`) so a rule is written once.

Site settings that render on every request (banner, homepage phase, Harvest
Fest page) are read through `unstable_cache` with a tag, and the action that
writes them calls `updateTag`.

## Routing

| Path | Purpose |
| --- | --- |
| `/` | Explorer. Phase 1 is a filterable grid and map of Seeds; Phase 2 shows a preview per stage. Toggled from Admin → Settings. |
| `/status/[slug]` | Listing for one stage (`seeds`, `sprouts`, `trees`) |
| `/seeds/new`, `/seeds/[id]`, `/seeds/[id]/updates/[updateId]`, `/seeds/[id]/qr` | Public project pages |
| `/dashboard` | "My Projects" |
| `/dashboard/projects/[id]/{edit,updates,supporters,team}` | Private workspace; the layout calls `getProjectWorkspace` once and sections trust it |
| `/admin` | Admin tabs |
| `/invite/[token]` | Accept a team invite |
| `/about`, `/faq`, `/harvest-fest` | Content pages fed from `config/content/` and `site_settings` |
| `/api/upload`, `/api/team-files/…` | Blob client-upload tokens and the authenticated private-file proxy |

`proxy.ts` (Next 16's middleware) redirects signed-out visitors away from
`/dashboard` and `/admin`, preserving the deep link as `callbackUrl`. Role
checks happen in the pages.

A handful of routes under `/seeds/[id]/*` and `/dashboard/seeds`,
`/dashboard/sprouts` are redirect shims for old bookmarks. Do not add links
to them.

## Adding a new object type

Say a city wants "Resources" that a Sprout team can list and offer. Follow the
stage-gated pattern rather than forking a parallel feature:

1. **Schema.** Add `project_resources` to `lib/db/schema.ts` with
   `project_id` (cascade delete), `created_by`, timestamps, and the fields.
   Add the relation on both sides. Run `pnpm db:generate` and commit the
   migration. Export the inferred types from `lib/db/types.ts`.
2. **Validation.** `lib/validations/resource.ts` with a Zod schema for the
   form payload. Limits belong here, not in the component.
3. **Queries.** `lib/db/queries/resources.ts`: `getResources(projectId)`
   selecting only rendered columns, ordered, and bounded.
4. **Actions.** `lib/actions/resources.ts` using `requireProjectAccess` (pick
   `manage` or `team`, and `requireWorkspace: true` if it is a Sprout+
   feature), `firstIssue`, `revalidateProject`, returning `ActionResult`.
5. **UI.** A client component in `components/projects/` that owns the form state
   and calls the action; render it from the right workspace section page
   (`app/dashboard/projects/[id]/team/page.tsx` for team features). Public
   display, if any, goes in `app/seeds/[id]/page.tsx`. Follow
   `docs/agents/design.md`.
6. **Navigation.** If it deserves its own section, add it to
   `ProjectWorkspaceSection` in `lib/routes.ts` and to
   `components/dashboard/project-workspace-nav.tsx`.
7. **Tests.** One file per action and query under `__tests__/`, mocking
   `@/lib/db` and `@/lib/auth-utils` the way the existing tests do. Component
   tests for the form.
8. **Sanitization.** If the data is private, add it to
   `scripts/sanitize-nonproduction.ts` so cloned databases drop it.

If the new type is not tied to a project (say, city-wide organizations), it
still follows steps 1–4 and 7, and gets its own route under `app/`. Keep
authorization in one function the way `lib/project-access.ts` does for
projects.

## Adding a city-level feature flag

Add a boolean under `features` in `config/site.ts`, gate the route with
`notFound()` and hide its admin tab, as `/harvest-fest` does. Document it in
`config/README.md`.

## Known rough edges

Things an audit flagged that are left for later:

- Naming: the data model, components and props say "project"; the public
  routes (`/seeds/…`) and all UI copy say "Seed", because that is the brand
  and the first lifecycle stage. `SeedIcon` is the Seed-anatomy icon set and
  keeps its name. Do not rename URLs.
- The in-memory rate limiter in `lib/actions/generate-image.ts` is per
  instance, so it is advisory on serverless. A durable limit would need a
  table or Runtime Cache entry per user.
- List queries are bounded (admin tables and comments page at the database;
  dashboard lists, the supporters page and the explorer map have fixed caps)
  but the public updates and team feeds still load a whole project's
  history. Fine at today's volumes; paginate when a project passes a few
  hundred posts.
- `scripts/populate.ts` is Chattanooga sample data. It runs through the
  same safety checks as the app but is not something another city should
  run as-is.
